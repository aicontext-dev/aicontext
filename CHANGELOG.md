# Changelog

All notable changes to the AIContext specification repository will be documented in this file.

Versions in this file are **tool/package versions** (`AIContext`, `AIContext.CLI`, standalone binaries). The specification has its own version (`0.1.0-draft`, `specVersion` `0.1.0`); format changes are marked as such below. See [SPEC.md section 9.1](./SPEC.md#91-specification-version-vs-tool-version).

## [Unreleased]

### Security

- **Sources of the context that lead outside the project are refused, and messages no longer repeat text that looks like a secret.** A symlink or junction inside the project can point anywhere, and the files of `.aicontext/` are read with the permissions of whoever runs the tool, so `.aicontext/README.md` linked to a file elsewhere on the disk, a `rules/` directory linked to another folder, or `.aicontext` itself a junction made `validate`, `export` and `status` copy that content into `AGENTS.md` and the other generated files (reproduced on Linux with file and directory symlinks and on Windows with a junction; `validate` only warned about a possible secret and exited with `0`, and the secret scan followed directory links wherever they led). A source whose real location (links resolved, as for export) is outside the project is now the error `AIC1008` and is not opened; `validate`, `export` and `status` apply it the same way and `export` writes nothing. Links that stay inside the project, and a project reached through a link, work as before. There is no option to allow an outside source. A directory is entered by the secret scan only once (by its real location), so a link cycle inside `.aicontext/` ends. Separately, five messages quoted text of a file (an unsupported or unknown line or key in a rule header, a rule path with `\`, a rule scope pattern in `status`, an unknown property name in `context.json`), so a secret placed there was printed although the scan never prints one; text that matches the scan patterns is now shown as `[redacted: looks like a secret]` and every other message is unchanged. The redaction is as heuristic as the scan. See D19. Library: `DiagnosticCodes.SourceOutsideProject`, `SecretScanner.Redact`. SPEC 10 now says implementations SHOULD NOT read sources outside the project root (a clarification; no change to the format or to `specVersion`).
- **Hard links were checked and are not a write leak.** A generated file or an orphaned nested `AGENTS.md` that is a hard link to a file outside the project is never changed through the link: an update goes through a temporary file that replaces the name, and a deletion removes only the name (tested on Windows and Linux, for `export`, `export --force` and `init --force`). A hard link cannot be told from a regular file, so a hard-linked source is read like any file; this is documented as a limit, not detected.
- **The security model and its limits are written down.** The user manual has a section "Security model and limits" (not a sandbox, symbolic links and junctions only, an export is not a transaction, the generated header is a convention and not authentication, the secret lint is a heuristic, the content is not judged, paths in messages, tested platforms), and there is a short [SECURITY.md](./SECURITY.md) with how to report a vulnerability privately.

### Fixed

- **Ordinary I/O problems no longer escape as exceptions, and the CLI no longer reports files as created before they were written.** A locked `.aicontext/README.md` made `validate`, `export` and `status` throw an `IOException` without a diagnostic; when `.github/copilot-instructions.md` was a directory, `export --target all` printed `Created` for every file, created `AGENTS.md` and then threw `UnauthorizedAccessException` (both reproduced). Now a file of `.aicontext/` that cannot be read is the error `AIC1007` (`AIC2006` for rules and the `rules/` directory), and the run fails with exit code `1`. A directory where a generated file has to go, or a file where a directory is needed, is the error `AIC4105` in the plan, and an existing file that cannot be read, or that is locked or read-only when it is about to be overwritten, is `AIC4106`; both are found before the first file is written, so nothing is written (also visible with `--dry-run` and `--check`). `init` does the same for its files, with `--force` too.
- **A failed write no longer damages an existing file.** An existing generated file used to be truncated before its new content was written, so a write that failed midway (no space, a lock) could leave it empty or half-written. It is now written to a temporary file in the same directory and swapped in, and the temporary file is removed on every failure. A link is still overwritten in place (replacing it would change what the destination means), a read-only or locked file is not replaced, the permission bits of the old file are kept on Unix, and the planned content is verified once more right before the swap. A new file that could not be written completely is removed again. Not preserved: the owner and extended attributes of the old file, and a hard link to it is no longer the same file. The directory of the file must allow creating files, otherwise the write fails (`AIC4106`) instead of overwriting in place.
- **The result of `export` and `init` is truthful when a write fails midway.** An export or an init is a sequence of single-file writes, not a transaction. When a write fails after the plan was verified, writing stops, the error is `AIC4106`, and the output says exactly what happened: `Created`/`Updated`/`Removed` only for files that were written, `Not written` for the rest, and `Only N of M changed file(s) were written`. The files written before the failure stay, nothing is rolled back, and `aicontext export` run again plans from the files as they are and finishes the job. A plan is announced as a plan (`Would create …`); `Created …` is printed after the write. Library: `ExportResult.Written` lists the completed files, `ExportResult.Unchanged` now counts only files that were already up to date (it also counted unwritten files after a failure), `InitResult` lists in `Created` what was really written when it stops midway, and `StaleExportPlanException` has a `Reason`. New codes `AIC1007`, `AIC2006`, `AIC4105`, `AIC4106`. Unexpected exceptions (bugs) are still not caught.
- **Export no longer lets a link target containing `..` after another link carry a file out of the project.** The path guard cancelled `alias/..` in the text of a link target before it followed `alias`, which is itself a link, so on POSIX it checked a different directory than the one the file system wrote to. A link `.github -> alias/../landing` with `alias` pointing outside the project made `export` create, overwrite and delete generated files outside the project, or inside a separate project (reproduced on Linux for create, update and delete; the same plan was re-verified before applying and let through). The guard now follows links one component at a time in the order the file system does, and accepts a path only when it is inside the project under both readings of `..` in a link target (the real directory reached so far, as POSIX does, and the text cancelled first, as Windows is believed to do). A path that is safe under one reading only is refused (`AIC4102`, or `AIC4104` for a separate project) with a message that says the platforms resolve it differently. The nested `AGENTS.md` mapping uses the same two readings. Links that stay inside the project work as before; a refused case is a target with `..` after a link whose two readings differ and one of them leaves the project. The compound-link tests did not escape on `windows-latest`, so the Windows behavior is covered by the conservative rule and not shown to be exploitable.
- **Export no longer decides letter-case equality by operating system.** The guard compared paths ignoring case on Windows and macOS, so inside a case-sensitive directory (a per-directory attribute on Windows, a case-sensitive volume on macOS) a link to `Proj` was taken for a link into the project `proj`, and export created, overwrote and deleted files there (reproduced on Windows for all three). Two spellings that differ only by case now count as the same directory only when the directory listing shows one entry, so links on ordinary case-insensitive volumes keep working whichever spelling the project path and the link target use. Where this cannot be shown (several entries that differ only by case, or a directory that cannot be listed) the path is refused. Not verified on macOS.
- **`init` no longer writes through a link that leaves the project.** `init` only checked whether the target files existed, then created `.aicontext/` and wrote the files, so a `.aicontext` junction or symlink pointing outside the project made it create `README.md`, `context.json` and the Extended starter files there, and an existing or dangling file link let it overwrite or create a file outside (with `--force`, or without it for a link to a file that does not exist; reproduced on Linux and on `windows-latest`). `init` now checks every destination with the same path guard as export before it writes the first file, and refuses the whole run (nothing written, exit code 1) when one of them leaves the project (`AIC4102`) or enters a separate project (`AIC4104`). `--force` still only allows overwriting files inside the project. New files are created exclusively, as in export, so a file that appears after the check is reported as a conflict and never overwritten. Links that stay inside the project and a normal `init` or repeated `init` behave as before. Library: `InitResult.Diagnostics` and `InitResult.HasErrors`. Exit code and options of `init` are unchanged.
- **Rule files have one exact frontmatter grammar, and a header that cannot be read as written no longer produces a broader rule.** The parser, the loader and SPEC 4.4 disagreed, and several ordinary inputs changed the scope of a rule without a word (all reproduced with the CLI): `paths: []`, `paths:`, `paths: ""` and `description:` made the rule **always on**; the second of two `paths` keys silently replaced the first; a comment such as `paths: [a, b] # note` became part of the patterns (`[a` and `b] # note`); an apostrophe inside an item (`paths: [src/it's/**, lib/**]`) swallowed the comma and produced one pattern; `paths: "a", "b"` produced the single pattern `a", "b`; an unknown key with a nested value rejected the whole rule although SPEC says unknown keys MUST be ignored; and the names `_team.md` and `-team.md` were rejected although SPEC allows them. SPEC 4.4.1 now defines the subset (not YAML): the block, key lines, scalars, quoting, flow and block lists, `#` comments, nested values and what each known key accepts. A rule whose `paths` or `description` is present but empty is invalid (`AIC2007`) and is never exported, in particular not as an always-on rule; a repeated key (also an unknown one), an unterminated quote, text after a closing quote, a quoted item in a list without brackets, and a nested value under `paths` or `description` are errors (`AIC2003`, `AIC2004`); the value of an unknown key is not interpreted at all and only produces the warning `AIC2103`. The language-neutral rule fixtures of the new `ruleCases` in the [conformance suite](./conformance/README.md) cover the accepted and the rejected files, and the README of the suite says how an independent implementation runs them. No change to `context.json`, its schema or `specVersion` (a clarification within the draft). **Compatibility:** rules that were accepted before and are errors now: empty `paths`/`description`, a repeated key, a quote that is not closed or followed by text, `paths: "a", "b"` and `paths: a, "b"`. Rules that were errors and are accepted now: names with a leading `_` or `-`, and unknown keys with nested values (warning). Silent changes of meaning: a `#` after whitespace outside quotes now starts a comment, also in `description` (`description: Fix #12` is `Fix`; write `"Fix #12"`), and an apostrophe inside an item no longer swallows the commas. `paths: "src/**, lib/**"` still has two patterns. Library: `FrontmatterValue` has the optional members `IsNested`, `Problem` and `Quoted`, `Frontmatter.ReadItems` reads the items of a list-valued key, and `Frontmatter.SplitTopLevel` recognizes a quote only at the start of an item; new code `DiagnosticCodes.EmptyFrontmatterValue` (`AIC2007`). `.gitattributes` keeps the conformance fixtures LF.
- **A lone CR is a line break like LF and CRLF, so the line endings of a source no longer change a rule, a hash or an export.** The normalization replaced only CRLF, in five separate places (the exporter, the file comparison of the writer, the frontmatter parser and the two scanners), so a text with a lone CR was not normalized at all. Reproduced with a rule file on the code before this change: the scoped rule `---\rdescription: UI conventions\rpaths: ["src/ui/**"]\r---\rBody` was loaded as an **always-on** rule whose body starts with `---\rdescription: …` and no diagnostic, a mix of endings (LF, CR, CRLF) loaded the same rule as **on-demand** with its `paths` swallowed into the description, an export of sources with CR endings contained `\r` although the output is documented as LF only (the audit's F05; `Summary.\rLine.`), the source hash differed from the one of the same text with LF, a README heading with CR endings was not removed, and the line numbers of findings differed between the file scan (which counts a lone CR as a break) and the text scan. There is now one helper, `LineEndings.Normalize` (CRLF, then CR, to LF; nothing else is a break: U+0085, U+2028 and U+2029 stay), and every place that parses, hashes, scans or writes text uses it: `ContextExporter` (sections, README, rule bodies and descriptions, the project name, the source hash), `ExportWriter` (the generated-file check and the unchanged comparison), `Frontmatter.Parse`, `SecretScanner.Scan` and `PlaceholderScanner.Scan`. SPEC 6.2 and 4.4.1 say so. **Unchanged:** text with LF or CRLF endings, which is every ordinary project: the source hash of LF sources and every generated file are byte for byte the same as before (checked on the `.aicontext/` of this repository and on a project with all kinds of rules for all seven targets in both layouts, and by `export --target all --check`), and the order in which public rules are hashed is not changed. Only the hash and the output of sources with a lone CR change (they now equal those of the same text with LF), and `LineEndings` is internal, so there is no API change. The new `LineEndingTests` run LF, CRLF, CR and a mix through the helper, the parser, the loader, the hash, every target in both layouts, nested `AGENTS.md`, the whole path from files to the plan, generated files rewritten with other endings, and the scanners; `SourceHashContractTests` pins the hash of an LF context, which was verified against the code before the change.
- **A scoped rule is no longer loaded outside its scope through its description in Copilot.** The scoped Copilot file had both `applyTo` and `description`. The VS Code documentation (custom instructions reference and "Use custom instructions", checked on 2026-11-11; the tools were not run) says that in the **Local** harness a `description` lets the agent load an instructions file by relevance, separately from `applyTo` and not as a condition on it, so a rule whose source says `paths: ["tests/**"]` could be loaded for any file; this repository's own `aicontext-tests.instructions.md` had both fields. A scoped Copilot file now has `applyTo` alone, and the description is kept as a `Description:` line in the body, so it is not lost. Not changed: always-on rules (main file), on-demand rules (Copilot keeps them in the main file with a "Use when: …" line, as SPEC 6.4 documents), the single layout, and the other tools; Cursor, Windsurf and Devin keep the `description` field of a scoped rule because their documentation does not show an independent trigger for a rule that has a path scope (not a claim that they have none). The Copilot harness and GitHub's Copilot features document `applyTo` only, and the Local harness is documented as deprecated (removal planned for February 2027). SPEC 6.4 now says that the description of a scoped rule MUST NOT be written as a field a tool documents as an independent trigger and SHOULD be kept as text. **Compatibility:** the first `aicontext export` after upgrading rewrites every `.github/instructions/aicontext-*.instructions.md` (the `description:` line moves into the body); no source file, `context.json`, schema or `specVersion` changes. Library: no API change. Tests: the new `CopilotScopedRuleTests` cover scoped, always-on and on-demand rules, the single layout, the other tools and the update of a file generated by an earlier version. See D22.
- **The patterns of `paths` have one meaning in every tool, and a rule whose scope a tool cannot be told is refused instead of being written with another scope.** The same pattern text was copied into every tool, and the tools read it differently (checked against their documentation; the tools were not run): `*.ts` is the root-level files for Copilot and Cursor and the files at any depth for Claude; Copilot's `applyTo` and Cursor's `globs` are one comma-separated text, so `paths: ["src/a,b/**"]` was written as `applyTo: "src/a,b/**"`, which they read as two patterns (`src/a` and `b/**`), and `src/**/*.{ts,tsx}` was cut at the comma; Windsurf and Devin document one pattern with a `/` and no separator or root-level form. SPEC 4.4.2 now defines the meaning: a pattern is relative to the project root and matches the whole path (`*.ts` is the root only, `**/*.ts` any depth), `*` and `**` as a whole segment, one level of `{a,b}` as a shorthand for separate patterns (at most 64), a comma in an item of a list as a literal character, letter case significant, and dot names matched by `*` and `**`. A pattern outside that (`**` alone, a leading or trailing `/`, `.` or `..`, an empty segment, `a**b`, `? [ ] ( ) !`, a brace group that is nested, empty, unclosed or too large) is the error `AIC2008` and the rule is not exported. Each tool then gets only a form its documentation says means the same: Claude gets `/*.ts` for a root-level pattern, a brace group is written out as separate patterns for everyone, and where no such form is documented the export fails with the new error `AIC4107` that names the rule, the pattern and the tool, writes nothing at all (also nothing is deleted, and an existing generated file stays as it is), and never moves the rule into the always-on main file. That is the case for a comma in a pattern (Copilot, Cursor, Windsurf, Devin), and for several patterns or a pattern without `/` (Windsurf, Devin). It is different from the documented fallbacks, which stay: on-demand content stays inline for Copilot and Claude, and rules stay as sections with "Applies to: …" for Agents, Aider and the single layout. `aicontext status` shows such a target as `blocked` and prints the reason. Nested `AGENTS.md`: `<dir>/**` and `<dir>/**/*` map to a directory as before, while `<dir>` (a file) and `<dir>/` (not a pattern) stay in the root file with a reason. The [conformance suite](./conformance/README.md) has `globFiles`, 23 `globCases` with exactly the files each pattern matches (among them root-only patterns, `src/a,b/**`, dot names and letter case) and 20 `globInvalid` items, plus seven more rule fixtures. No change to `context.json`, its schema or `specVersion`; the draft rule chapter changes (SPEC 4.4, 4.4.2, 6.4), and SPEC 9.1 and GOVERNANCE 6.1 now say that a change of what a rule file means is recorded in the table of 9.1 and here, because rule files carry no version. **Compatibility and migration:** a pattern without `/` now means the root only for Claude too (`*.md` was any depth there: write `**/*.md`, or keep `*.md` for the root); `src/**/*.{ts,tsx}` now works in Copilot and Cursor, and is refused for Windsurf and Devin (several patterns); `["src/a,b/**"]` is refused for Copilot, Cursor, Windsurf and Devin and unchanged for Claude; and `**`, `src/`, `./src/**`, `/src/**` and `app/[id]/**` are errors (write `**/*`, `src/**`, `src/**`, `src/**` and `app/*/**`). A project whose multi-pattern rule is exported to Windsurf or Devin has to export without them, or split the rule into one rule per pattern. Library: `PortableGlob` (`Parse`, `IsMatch`, `MaxExpansions`), `ExportOutput.Problem`, `TargetStatus.Problems`, and the codes `DiagnosticCodes.InvalidRulePathPattern` (`AIC2008`) and `DiagnosticCodes.ScopeNotRepresentable` (`AIC4107`). See D21.

### Changed

- **A release is made from one verified commit and publishes only what was tested.** `publish.yml` was a manual checkout, pack and push of whatever ref was selected, without tests, strict validation, export check or any comparison of the version with a tag, and `release-binaries.yml` built from a tag by name and uploaded with `--clobber`, so nothing tied the NuGet packages and the binaries of a version to the same commit or to a passing check. Now one run of `publish.yml`, started from the release tag (Use workflow from: Tag vX.Y.Z, with "publish" ticked), uses `github.sha` for every job. It checks that the tag is named `v<version>`, that `AIContext` and `AIContext.CLI` have that version, and that the tag still points at the commit (again right before publishing); runs the checks of `pr-checks.yml` through a reusable call (strict validation, export check, build, tests on .NET 9 and 10 on Linux and Windows); packs the NuGet packages once and smoke-tests those exact files (the tool on .NET 9 and 10, the library on .NET 9 and 10, never a published copy of the same version); builds and smoke-tests the standalone binaries, which must report the tag's version; and only then attaches the binaries to the existing GitHub release and pushes the packages (the reversible step first). Nothing is replaced: `--clobber` and `--skip-duplicate` are gone, and an existing release asset, or an existing `AIContext`/`AIContext.CLI` version on nuget.org, stops the run before anything is built or published. `AIContext.Spec` keeps its own version and is pushed only when that version is new; an existing version is skipped with a notice. Trusted Publishing is unchanged (the same workflow file name, `NuGet/login` in the second to last step, `id-token: write` on that job only), and permissions are `contents: read` everywhere except the job that uploads release assets. Without "publish", and on pull requests that change release files, the workflow is a dry run: everything is built and tested, nothing is published and no token is requested. The binaries are no longer built when a GitHub release is published: the release must exist, and the workflow is started by hand. The job names of the pull request checks are unchanged. The shell scripts are in `.github/scripts/` and `.gitattributes` keeps them LF. Procedure, recovery and what is not verified: [RELEASING.md](./RELEASING.md).

## [0.6.0] - 2026-11-09

This release closes the gaps found while testing 0.5.0. It makes the export safer when a plan is applied later or a link points into another project, warns about leftovers of dropped targets, states the rules of `context.json` in the specification itself, and brings the documentation in line with what the tools really do (Aider and Copilot need a step of their own). Nothing changes the format: `specVersion` stays `0.1.0` and no `context.json` that was valid before is rejected. Library users should read the compatibility note at the end of **Changed**.

### Fixed

- **`ExportService.Apply` refuses a plan that went stale.** It used to write a previously prepared plan without looking at the disk again. A hand-written file created after planning was overwritten without `--force`, and a directory replaced by a junction after planning let the old plan write outside the project (both reproduced). `Apply` now verifies every file before writing anything: the path must still resolve inside the project, and the file must still be in the state it was planned for (content hash; a file that did not exist must still not exist). New files are created exclusively. A stale plan is reported as the new error `AIC4103` (or `AIC4102` for a path that now leaves the project), nothing is written, and `ExportResult` carries the diagnostics (`Diagnostics`, `HasErrors`); the CLI prints them and exits with 1. The short gap between the last check and the write of an existing file remains and is documented in D12. Library: `ExportFilePlan.ExistingHash`, `StaleExportPlanException`, `DiagnosticCodes.StaleExportPlan`. Most relevant for editor integrations that show a plan before applying it; no change for normal CLI use. SPEC 6.3 now says that an implementation which plans first and writes later SHOULD verify again before writing (a clarification; no change to the format or to `specVersion`).
- **A junction or symlink can no longer carry an export into a separate project.** The boundary of a directory with its own `.aicontext/` (D11) was checked on the path as written, so a link in the parent project that pointed into the nested project (or below it) bypassed it, and the parent export created files there (reproduced with a Windows junction). The nested-`AGENTS.md` mapping now also resolves the directory, so such a rule stays in the root file, and the path guard refuses every file whose real directory lies in a separate project, for all targets and for deletions too. The new error is `AIC4104`; `Blocked` in `status` now also covers this case. Links that stay inside the project and projects that are themselves nested in another project work as before. SPEC 6.4 now names links explicitly (a clarification; no change to the format or to `specVersion`). Library: `DiagnosticCodes.PathInSeparateProject`, `ExportFilePlan.ReasonCode`. Tested with junctions on Windows; the symlink case uses the same code path on Linux/macOS.

### Added

- **A warning for generated files of a target that is no longer exported.** After a target was removed from `exports.targets`, its generated files stayed on disk and `export --check` still said "Export is up to date", although a tool can keep loading them (Copilot in VS Code reads `AGENTS.md` and `CLAUDE.md` even when only `copilot` is exported). `export --target all` (also with `--check` and `--dry-run`, and with `defaultTarget: "all"`) and `status` now print one `WARNING` per such target that lists its leftover files (main file, `aicontext-*` rule files, nested `AGENTS.md`), names the tools that also read them and says how to resolve it. It is the new warning `AIC4201`: it never blocks, never changes an exit code, and an explicit single `--target` does not report anything. Only files with the generated header are reported, never hand-written ones. Nothing is deleted automatically; see D17. Library: `DiagnosticCodes.OrphanedTargetExport`, reported in `ExportPlan.Diagnostics` and `StatusReport.Diagnostics`.
- **`aicontext status` shows overlap between exported files.** Some tools read several of the exported files and load them together (Copilot in VS Code combines `.github/copilot-instructions.md`, `AGENTS.md` and `CLAUDE.md`), so the per-target table understated the real always-on context. `status` now adds an "Overlap" section with the summed always-on size for such tools (Copilot, Cursor, Devin), built from a small table taken from the vendors' documentation and labelled as an estimate. It is informational only, not a `validate` warning. Library: `ToolOverlaps`, `ToolOverlap`, `StatusReport.Overlaps`.
- **`validate` reports obvious placeholder text** (`TODO: ...`, a value that is only `TODO` such as `**Tech stack:** TODO`, the starter summary line of `init`) in `README.md`, the section files and `rules/*.md` as the warning `AIC1107`. Code blocks and inline code are ignored, and a line can opt out with `aicontext:allow-placeholder`. Library: `PlaceholderScanner`, `DiagnosticCodes.PlaceholderContent`.
- `aicontext init` prints a hint to replace the `TODO` placeholders, and a successful `validate` states that it checks structure and obvious placeholders, not whether the content is useful or up to date.
- **Language-neutral conformance suite** in [conformance/](./conformance/README.md) for the draft format `0.1.0`: 24 `context.json` examples (6 valid, 18 invalid) with the expected outcome, the JSON Pointer where an error is expected, and the SPEC section each case follows from (5.1 or 5.2). Cases marked `beyondSchema` are the rules a JSON Schema evaluator with default settings does not enforce. Independent implementations can run it, and the reference implementation runs it in its tests (which also check that every fixture is listed in the manifest, that every case names an existing SPEC section, and that SPEC 5.1 describes every property of the schema).
- **Help for projects that already have instruction files.** `aicontext init` lists the hand-written instruction files it finds (`AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, ...) and points to the migration recipe; a failed `export` because of such a file points to it as well. Nothing about overwriting changes. Library: `ProjectInitializer.FindExistingInstructionFiles`. The recipe in the user manual (chapter 11, B) is now a step-by-step procedure. The search also covers hand-written files in the tools' rule directories (`.github/instructions/`, `.claude/rules/`, `.cursor/rules/`, `.windsurf/rules/`, `.devin/rules/`) and nested `AGENTS.md` files (outside separate projects), says that such files are never touched by export and stay active next to the generated rules, and says that other places are not searched. At most ten files are listed.
- **"Does my tool read the generated file?" in the user manual (chapter 6), with short notes in the README and on the website.** Generating a file does not mean every tool loads it: Aider does not read `CONVENTIONS.md` unless started with `--read CONVENTIONS.md` or configured with `read:` in `.aider.conf.yml`, and which files Copilot in VS Code reads depends on the agent (Copilot, Claude or Local) and on its settings (`chat.useAgentsMdFile`, `chat.useClaudeMdFile`, `chat.useNestedAgentsMdFiles`, `github.copilot.chat.codeGeneration.useInstructionFiles`, `chat.includeApplyingInstructions`). The chapter also summarizes what Claude Code, Cursor, Windsurf/Devin and tools that read `AGENTS.md` load by themselves (for example Claude Code reads `AGENTS.md` only when there is no `CLAUDE.md`), based on the vendors' documentation as of November 2026, and the quick-start no longer promises that every assistant "now knows your project".
- **README and website.** The front page and the website now start with the problem, the result, who the project is for (and not for), how existing files are handled, which tools are supported and with what limits, a short real example and links to install and the guides.

### Changed

- **The rules of `context.json` are now stated in the specification, so the conformance suite verifies them instead of introducing them.** New SPEC 5.1 lists every property with its type, whether it is required and its rule, including the ones the suite relied on but the text did not say: unknown properties are errors at every level, `project.name` must contain a non-whitespace character, `exports.defaultTarget` must be `all` or listed in `exports.targets` (when that is set), and `metadata.lastReviewed` must be a real `YYYY-MM-DD` date. New SPEC 5.2 explains the two rules a JSON Schema evaluator does not enforce by default (the `defaultTarget` cross-check, and `format` assertion for dates) and requires implementations to enforce them in addition to the schema; SPEC 7 and 8.1 refer to it. The schema now also says the whitespace rule itself (`pattern: "\\S"` on `project.name`) and documents the two other rules in `description`. The reference implementation behaves as before: a whitespace-only name is still reported as `AIC1005` (now derived from the schema instead of a separate check, without a duplicate `AIC1004`), and no document that was valid before is rejected now. Draft-period clarification within `0.1.0`; `specVersion` is unchanged.
- **`validate --strict` now fails for a project that still contains starter placeholders.** A freshly initialized extended project used to pass `validate --strict` as the Extended profile although its files said `TODO`, and `export` sent those stubs to AI tools as real context. The profiles stay structural, a plain `validate` still passes (exit 0), and only `--strict` turns the warning into an error. The standalone-binary smoke test now expects exactly this.
- SPEC 7 and 8.2 state that placeholder detection is an optional heuristic and that the profiles describe structure only. No change to the format or to `specVersion`.
- GOVERNANCE 6.1 and 6.2 document the draft-period exception to the compatibility commitment (additive changes within `0.1.0`, as already described in SPEC 9.1) and what the maintainers plan to decide before the first stable release (immutable schema versions, how an implementation reacts to newer documents, the conformance suite). SPEC 14 links to the suite. No change to the format or to `specVersion`.
- **Compatibility note for library users.** `ExportFilePlan` gained the optional constructor parameters `ExistingHash` and `ReasonCode`, `SchemaIssue` gained the optional `Keyword`, and `ExportResult` gained `Diagnostics` and `HasErrors`. Source code keeps compiling, but a program built against 0.5.0 has to be recompiled. `ExportService.Apply` can now return a result with errors (stale or unsafe plan) instead of always succeeding: check `HasErrors`. Plans built by hand without `ExistingHash` are treated as stale when the file exists.

## [0.5.0] - 2026-11-08

This release hardens the CLI and the export. It fixes problems that could delete or write files outside the intended place, and problems that let a broken or mistyped invocation pass silently in CI. Some of these fixes change behavior that scripts may have relied on: see **Changed** first.

### Changed

- **The CLI rejects invalid arguments before running a command** (exit code 1, nothing is validated, exported or written). Previously unknown options were ignored, so `validate --strcit` passed without `--strict`, `export --chek` wrote files instead of checking them, and `init --path --force` (value missing) ran in the current directory and overwrote existing files. Now an unknown option, an option that belongs to another command, an option without its value, a repeated option and a non-boolean value after a flag (`--strict no`) are errors. Flags still accept an explicit `true`/`false`/`1`/`0`. Scripts that relied on the old lenient behavior must be corrected.
- The CLI logic moved from top-level statements to `AIContext.Cli.CliApp` (`CliApp.Run(args, output, error, workingDirectory)`) so it can be tested in-process. Output and exit codes of valid commands are unchanged; the overview from `--help` lists the commands in usage order.
- **`export` and `status` refuse what `validate` reports as an error.** Previously `export` only checked that the files exist and parse, so an unsupported `specVersion` (for example `999.0.0`), a wrong type, an unknown property or a `context.json` that was not an object still produced files while `validate` failed. Now `ContextLoader.Load` applies the same checks as `ValidateDirectory` and returns its errors; warnings (missing recommended files, possible secrets, ...) never block export or status. `export` prints every such error with the `ERROR:` prefix followed by `No files were written.`
- SPEC 6.3, 6.4 and 7 state the new requirements (no writes outside the project, separate projects, export applies validation errors). No change to the format or to `specVersion`.
- **Export and status are driven by the new `ExportService`; the CLI only prints.** Output of valid commands is unchanged. Errors that were printed bare now carry the `ERROR:` prefix and are followed by `No files were written.`: unsupported export target, missing target, unsupported `exports.defaultTarget`, unsupported layout (and `ERROR:` for the same problems in `status`). The extra line `Run 'aicontext validate' to see full details.` for an invalid `exports.targets` is gone (the schema check now catches those cases first).
- **Library result records changed shape.** `ContextValidationResult(Diagnostics, ExtendedProfile)`, `RuleLoadResult(Rules, Diagnostics)` and `ContextLoadResult(Loaded, Diagnostics)` carry a list of diagnostics; `Errors` and `Warnings` remain as read-only views with exactly the same messages as before. Code that only reads these properties is unaffected; code that constructs the records must be updated.

### Added

- `aicontext <command> --help` (also `-h`) prints the usage and options of a single command.
- CLI tests for argument validation, exit codes and the `init` / `validate` / `export --check` workflow. The test job in `pr-checks.yml` now runs on Ubuntu and Windows.
- `ExportFileStatus.Blocked` and `SyncState.Blocked` (with `ExportFilePlan.Reason`), and `ContextSchema.CanonicalUrl`, in the core library. `aicontext status` shows `blocked` for a target whose files would leave the project through a link.
- `SecretScanner.ScanDirectoryReport` (with `SecretScanReport` and `UnscannedFile`) returns the findings together with the files it could not scan; `ScanDirectory` still returns only the findings. `validate` warns `Secret scan incomplete for .aicontext/<file>: <reason>. Check it manually.` for such files, so `--strict` no longer passes a scan that was incomplete.
- **Stable diagnostic codes.** Every validation, rule, secret-scan and export problem is a `Diagnostic` (`Code`, `Severity`, `Message`, `Location`) with a code `AIC1001` ... `AIC4102` defined in `DiagnosticCodes` and listed in the user manual. Codes are never reused or renumbered; messages may change. `ContextValidationResult`, `RuleLoadResult` and `ContextLoadResult` expose `Diagnostics`.
- **`ExportService`** in the core library: `Plan(ExportRequest)` loads and validates the project, resolves target and layout, plans every file and reports overwrite conflicts and paths leaving the project as diagnostics; `Apply(ExportPlan)` writes a plan without errors and refuses one with errors; `Status(basePath, layout)` returns context size and sync state per target. Front ends no longer have to assemble the safe procedure themselves. See the library README.

### Fixed

- **`validate` no longer skips large files when scanning for secrets.** The scanner silently ignored every file above 512 KiB, so the same secret failed `validate --strict` in a small file and passed in a larger one (reproduced). Files are now read line by line without a size limit; a file that cannot be read, or a line that is too long or complex to check in time, is reported instead of being skipped (or crashing the scan). Files with other extensions than `.md`, `.mdc`, `.json`, `.yml`, `.yaml` and `.txt` are still not scanned, which SPEC 10, the README and the user manual now state together with the fact that the scan is a heuristic and no guarantee.
- **Exporting a project no longer deletes the generated `AGENTS.md` of an independent project in a subdirectory.** The cleanup of orphaned nested `AGENTS.md` files walked the whole tree, so a parent export removed a nested project's own file (even without `nestedAgents`) and `export --check` in that project then failed. A directory that has its own `.aicontext/` is now a project boundary: the cleanup skips it, and `nestedAgents` keeps a rule scoped to it (or below it) in the root file, with the reason shown by `status`. Orphan cleanup elsewhere is unchanged.

### Security

- **Export never writes or deletes outside the project through a symlink or junction.** The check that a nested directory lies inside the repository compared path text only, so a link inside the repository could send a generated `AGENTS.md` anywhere (reproduced with a Windows junction); the same applied to fixed output paths such as `.github/` and to removing orphaned rule files. Every path to be written or deleted is now resolved (links followed, also dangling file links) and must stay inside the real project root; links that stay inside are allowed, and a project reached through a link works. A violation is reported as `Blocked`; as with an overwrite conflict, nothing is written and the command fails (also with `--dry-run` and `--check`). Verified on Windows (junctions) and Linux (symlinks).

## [0.3.0] - 2026-11-02

### Added

- `exports.nestedAgents` (split layout): rules scoped to an exact directory are exported to nested `<directory>/AGENTS.md` files so tools that only read `AGENTS.md` load them on demand. Only exact directory scopes of existing directories are mapped; everything else stays in the root file. `status` lists nested files and why a rule was kept in the root file. Orphaned generated nested files are removed (the tree walk skips hidden, `node_modules`, `bin`, `obj`, `vendor`, `dist`, `build`, `target`, `venv` directories). See SPEC 6.4.

- **Rules and split export layout.** Optional `.aicontext/rules/*.md` with `description` and `paths` frontmatter, and `exports.layout: "single" | "split"` (also `aicontext export --layout`). In the split layout `README.md` and `constraints.md` stay in a small always-on file, while scoped and on-demand content is exported as native rule files: Cursor `.mdc` (`globs`, `description`), Copilot `.github/instructions/*.instructions.md` (`applyTo`), Claude `.claude/rules/*.md` (`paths`), Windsurf/Devin rules (`trigger`, `globs`, `description`). Where a tool cannot scope content (AGENTS.md, Aider; on-demand content in Copilot and Claude) it stays in the main file. See SPEC 4.4 and 6.4.
- `aicontext status` command: context size per tool (always on vs. scoped/on-demand, estimated tokens), export sync state, and a hint when the `split` layout would reduce always-on context.
- `ContextLoader` and `ExportStatus` in the core library (shared by `export` and `status`).
- `devin` export target (`.devin/rules/`). It is opt-in: excluded from the default `all` set, and `validate` warns when `windsurf` and `devin` are both enabled (Devin also loads `.windsurf/rules`).
- Generated rule files use the `aicontext-` prefix; `export` removes generated rule files whose source no longer exists and never touches other files.
- `validate` checks rule files (name, frontmatter, paths) and scans them for secrets.
- This repository now uses the split layout and a `tests` rule as a working example.
- `aicontext export --dry-run` and `aicontext export --check` (exit code 1 when exports are missing or out of date).
- Unit tests for determinism, line endings, safe-overwrite behavior, rules, and split exports.

### Changed

- `aicontext validate` now validates `context.json` against the real JSON Schema (embedded in the library from [schema/v1/context.schema.json](./schema/v1/context.schema.json), evaluated with JsonSchema.Net). This also catches unknown properties, wrong `specVersion`, duplicate/empty values, and invalid dates, which were previously not detected. Error messages now have the form `context.json <json-pointer>: <message>`.
- `ContextValidator.ValidateDirectory` signature simplified to `(basePath, canonicalSchemaUrl)`; `ContextValidationResult` now exposes `ExtendedProfile` instead of `LocalSchemaPath`. The "local schema file not found" warning was removed.
- CI (`pr-checks.yml`, `validate-aicontext.yml`) now runs `aicontext validate --strict` and `aicontext export --target all --check` through the CLI. The PowerShell script `scripts/validate-aicontext.ps1` (a hand-written subset of the same checks) was removed.
- Repository `.aicontext/` now includes `architecture.md`, `decisions.md`, `constraints.md`, `patterns.md` and `glossary.md` (Extended profile), and the `aider` target, so `CONVENTIONS.md` is kept in sync.
- SPEC 7 and 10 clarified (empty recommended files, schema embedding, secret lint behavior).
- Exports are now deterministic: the generation timestamp was removed from the generated header and replaced by `Source-hash: sha256:<hex>`; output always uses LF line endings regardless of OS. Unchanged files are no longer rewritten. Existing generated files are refreshed once on the next `export`.
- `export` no longer overwrites existing files that were not generated by aicontext (no `Auto-generated by aicontext export` header). It reports a conflict, writes nothing, and exits with code 1 unless `--force` is given.
- SPEC 6.1/6.2 updated (timestamp SHOULD NOT be included, source hash recommended) and new section 6.3 "Safe overwrite" added.
- Export logic (target paths, planning and writing) moved from the CLI into the core library ([ExportTargets.cs](./src/AIContext/ExportTargets.cs), [ExportWriter.cs](./src/AIContext/ExportWriter.cs)); the per-target builders are unified and no longer take a timestamp.
- All projects now multi-target `net9.0;net10.0`; the `aicontext` .NET tool package ships both, so it installs on either runtime.
- Test project runs on both `net9.0` and `net10.0`.
- CI and publish workflows install .NET 9 and .NET 10 SDKs.
- Repository `.aicontext` stack updated to `.NET 10` and generated exports refreshed.

### Fixed
