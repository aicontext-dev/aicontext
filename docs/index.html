AIContext

Maintain AI coding instructions in one place.
Validate them and export to supported tool formats.

Try the small demo · Report what was confusing

MIT licensed. The specification is a draft (0.1.0-draft) and the tools are 0.x, so formats and behavior can still change. See the changelog. Download the CLI without .NET.

AIContext is an open-source format and CLI for maintaining shared project instructions, generating tool-specific files, and checking for stale exports in CI. Keep the source in .aicontext/ as plain Markdown and JSON. Validation and export run locally, with no AI account or model calls.

It manages instruction files, not agent behavior. If one short hand-written file already works for you, you may not need it.

The problem

AI coding tools use different instruction files and loading rules. If you or your team maintain the same guidance in files such as AGENTS.md, CLAUDE.md and Copilot instructions, a change to one copy can leave the others out of date.

The result

You write the knowledge once in .aicontext/ (plain markdown), and aicontext export generates files for your selected targets. The output is deterministic, so unchanged sources produce no diff, and CI can check that the generated files are up to date.

Before: the same text kept by hand 
AGENTS.md
CLAUDE.md
.github/copilot-instructions.md
.cursor/rules/project.mdc
After: one source, generated files 
.aicontext/        <- you edit this
  README.md
  constraints.md
  rules/ui.md

AGENTS.md          <- generated
CLAUDE.md          <- generated
...                <- generated

Try it

Start with the Windows/Linux demo: a ready-to-copy sample and a pinned standalone CLI. No Git, .NET SDK or AI account is needed. Work in a separate practice folder.

After copying the sample and downloading the CLI, the workflow is:

validate -> export -> change one source rule -> check detects drift -> export

For example, in the demo's PowerShell terminal:

..\tools\aicontext\aicontext.exe validate
..\tools\aicontext\aicontext.exe export --target all
..\tools\aicontext\aicontext.exe export --target all --check

The sample configures only agents and copilot, so all means those two targets, not every supported tool. The first export prints: 

# the tool prints the full path of each file; shortened here
Created (agents): AGENTS.md
Created (copilot): .github\copilot-instructions.md
Export completed (2 changed, 0 unchanged).

The guide then shows a stale check (exit 1), an update, and a repeated export that changes nothing. These targets demonstrate file synchronization; some tools can load both files, so this is not a universal configuration recommendation. Continue with scoped rules or CI checks.

Is it for you?

A good fit
  • You or your team use two or more AI coding tools, or expect to.
  • You want project guidance reviewed in pull requests like code.
  • A large repository or monorepo, where scoped rules can reduce always-on content where the target supports them (split does not bound context size).
  • CI should catch stale exports and flag obvious placeholders or possible secrets.
Probably not (yet)
  • You use a single tool and a short hand-written file already works: keep it.
  • You expect AIContext to write or judge the content: validation checks structure and flags obvious placeholders or possible secrets; it does not generate content or judge its usefulness.
  • You need to enforce what an AI tool does: the context is guidance, not policy enforcement.

Your existing files

AIContext protects hand-written instruction files by default.

  • export replaces only files that carry the Auto-generated by aicontext export header. Any other existing file is a conflict: nothing is written until you pass --force.
  • aicontext init lists the hand-written instruction files it finds, and export --dry-run shows what would change. The user manual has a step-by-step migration recipe (chapter 11, B).
  • Export never writes or deletes outside the project, even through symlinks or junctions, and refuses a context.json that validate rejects.

Supported tools and their limits

ToolGenerated fileScoped rules (split layout)
GitHub Copilot.github/copilot-instructions.md.github/instructions/*.instructions.md
Claude CodeCLAUDE.md.claude/rules/*.md
Cursor.cursor/rules/*.mdc.mdc rules with globs or a description
Windsurf.windsurf/rules/*.mdrules with a glob or model-decision trigger
Devin (opt-in).devin/rules/*.mdsame format as Windsurf
AiderCONVENTIONS.mdnone (one file)
Tools that read AGENTS.mdAGENTS.mdnone; optional nested AGENTS.md per directory
  • The per-tool rule formats follow the vendors' documentation; they have not yet been verified against every tool in real projects.
  • Some tools read several of these files together (for example the Local agent of Copilot in VS Code reads AGENTS.md and CLAUDE.md too). aicontext status shows the context size per tool and these overlaps as an estimate.
  • A tool does not always read its file without help: Aider only reads CONVENTIONS.md when you start it with aider --read CONVENTIONS.md (or set read: CONVENTIONS.md in .aider.conf.yml), and some editors have settings for file-based instructions (for example in VS Code with Copilot). See “Does my tool read the generated file?” in the user manual.
  • The secret lint is a heuristic and does not replace a dedicated secret scanner.
