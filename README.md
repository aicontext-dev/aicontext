# aicontext

> Open format standard for AI coding assistant project context.
> One source of truth. Every AI tool.

**Specification and tooling — work in progress.**
⭐ Watch/Star this repo for updates.

## What is this?

`.aicontext/` is an open directory format for storing structured
project knowledge that AI coding assistants can use.

Works with: GitHub Copilot · Cursor · Claude Code · Windsurf · Devin · Aider · any tool that reads `AGENTS.md`

## The problem

Every AI coding assistant reads its own instruction file: `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, `.cursor/rules/`, `.windsurf/rules/`, `CONVENTIONS.md`. A team that uses more than one tool writes the same project knowledge several times, and the copies drift apart.

## The result

You write the knowledge once in `.aicontext/` (plain markdown) and `aicontext export` generates each tool's file from it:

```text
Before: the same text kept by hand        After: one source, generated files
  AGENTS.md                                 .aicontext/              <- you edit this
  CLAUDE.md                                   README.md, constraints.md, rules/ui.md, ...
  .github/copilot-instructions.md           AGENTS.md, CLAUDE.md, ... <- generated, never edited
  .cursor/rules/project.mdc
```

The output is deterministic (no timestamps, always LF), so unchanged sources produce no diff, and CI can verify that the generated files are up to date.

## Try it

```powershell
aicontext init --name my-project       # creates .aicontext/README.md and context.json
# edit .aicontext/README.md: what the project is, its stack, rules that must never be broken
aicontext validate                     # schema, recommended files, placeholders, possible secrets
aicontext export --target all          # writes AGENTS.md, CLAUDE.md, .github/copilot-instructions.md, ...
aicontext export --target all --check  # in CI: exit code 1 when the generated files are out of date
```

```text
Created (agents): AGENTS.md
Created (copilot): .github\copilot-instructions.md
Created (claude): CLAUDE.md
Created (cursor): .cursor\rules\project.mdc
Created (windsurf): .windsurf\rules\project.md
Created (aider): CONVENTIONS.md
Export completed (6 changed, 0 unchanged).
```

## Is it for you?

A good fit:

- you or your team use two or more AI coding tools, or expect to;
- you want project guidance reviewed in pull requests like code;
- a large repository or monorepo, where scoped rules keep the always-on context small (the `split` layout, nested `AGENTS.md`);
- CI should catch drift, stray secrets and an unfinished context.

Probably not (yet):

- you use a single tool and a short hand-written file already works for you: keep it;
- you expect AIContext to write or extract the context for you: it does not generate or judge content, and a passing `validate` only means the structure is right and no obvious placeholder or secret was found;
- you need to enforce what an AI tool does: the context is guidance, and policy enforcement is a non-goal of the specification.

## Your existing files

AIContext does not overwrite what you already have.

- `export` replaces only files that carry the `Auto-generated by aicontext export` header. Any other existing file is a conflict: nothing is written (not even the other files) until you pass `--force`.
- `aicontext init` lists the hand-written instruction files it finds, and `aicontext export --dry-run` shows what would change. The user manual has a step-by-step migration recipe (chapter 11, B); git keeps your originals.
- Export never writes or deletes outside the project, even through symlinks or junctions, and refuses a `context.json` that `validate` rejects.

## Supported tools and their limits

| Tool | Generated file | Scoped rules (`split` layout) |
|---|---|---|
| GitHub Copilot | `.github/copilot-instructions.md` | `.github/instructions/*.instructions.md` (`applyTo`) |
| Claude Code | `CLAUDE.md` | `.claude/rules/*.md` (`paths`) |
| Cursor | `.cursor/rules/*.mdc` | `.mdc` rules with `globs` or a description |
| Windsurf | `.windsurf/rules/*.md` | rules with `trigger: glob` or `model_decision` |
| Devin (opt-in) | `.devin/rules/*.md` | same format as Windsurf |
| Aider | `CONVENTIONS.md` | none (one file) |
| Tools that read `AGENTS.md` | `AGENTS.md` | none; optional nested `AGENTS.md` per directory |

Limits to know about:

- The per-tool rule formats follow the vendors' documentation; they have not yet been verified against every tool in real projects.
- Some tools read several of these files together (for example the Local agent of Copilot in VS Code reads `AGENTS.md` and `CLAUDE.md` too). `aicontext status` shows the context size per tool and these overlaps as an estimate.
- A tool does not always read its file without help: Aider only reads `CONVENTIONS.md` when you start it with `aider --read CONVENTIONS.md` (or set `read: CONVENTIONS.md` in `.aider.conf.yml`), and some editors have settings for file-based instructions (for example in VS Code with Copilot). See "Does my tool read the generated file?" in the [user manual](./docs/user-manual.md).
- The secret lint is a heuristic and does not replace a dedicated secret scanner.
- The specification is a draft (`0.1.0-draft`) and the tools are `0.x`, so formats and behavior can still change; see the [CHANGELOG](./CHANGELOG.md).

## How to use schema

Use the canonical schema URL in your `.aicontext/context.json`:

```json
{
  "$schema": "https://aicontext.dev/schema/v1/context.schema.json",
  "specVersion": "0.1.0",
  "project": {
    "name": "my-project"
  }
}
```

Then validate locally:

```powershell
aicontext validate
```

## CLI (MVP)

### Standalone binary (no .NET required)

Download the archive for your platform from the [latest release](https://github.com/aicontext-dev/aicontext/releases/latest), extract it and put `aicontext` on your `PATH`:

| Platform | Asset |
|----------|-------|
| Windows x64 | `aicontext-win-x64.zip` |
| Linux x64 | `aicontext-linux-x64.tar.gz` |
| Linux arm64 | `aicontext-linux-arm64.tar.gz` |
| macOS Intel | `aicontext-osx-x64.tar.gz` |
| macOS Apple Silicon | `aicontext-osx-arm64.tar.gz` |

Verify the download against `SHA256SUMS.txt` from the same release. The binaries are not code-signed yet: on macOS run `xattr -d com.apple.quarantine aicontext` if Gatekeeper blocks a browser-downloaded file, and Windows SmartScreen may show a warning.

Quickstart (full guide: [User manual](./docs/user-manual.md)):

```powershell
aicontext init --name my-project
aicontext validate
aicontext export --target all
```

Note:
- `validate` checks `context.json` against the JSON Schema embedded in the tool (the same schema as [schema/v1/context.schema.json](./schema/v1/context.schema.json)), warns about missing or empty recommended files (`architecture.md`, `decisions.md`, `constraints.md`) and about obvious placeholder text such as `TODO: …` (add `aicontext:allow-placeholder` to a line where it is intentional), reports whether the repository meets the Core or Extended profile (which describe structure only, not whether the content is useful), and scans the text files in `.aicontext/` (`.md`, `.mdc`, `.json`, `.yml`, `.yaml`, `.txt`, of any size) for common secret patterns (private keys, cloud/API tokens, hard-coded passwords, credentials in URLs; the secret value is never printed). This is a heuristic, not a guarantee, and it does not replace a dedicated secret-scanning tool; files with other extensions are not scanned, and a file that cannot be read is reported as a warning. Add `aicontext:allow-secret` to a line to mark an intentional example. Use `--strict` to treat warnings as errors (useful in CI).
- `export --target all` uses `exports.targets` from `.aicontext/context.json` when configured.
- `export` only overwrites files that carry the `Auto-generated by aicontext export` header. Any other existing file is reported as a conflict and nothing is written unless you pass `--force`.
- `export` output is deterministic (LF line endings, no timestamp; a `Source-hash` in the header identifies the sources), so unchanged sources never produce a diff. Unchanged files are not rewritten.
- `--dry-run` shows what would change; `--check` does the same and exits with code 1 when exports are missing or out of date (useful in CI).
- Invalid arguments never run a command: unknown options (for example a mistyped `--strcit`), missing option values and repeated options are rejected with exit code 1. `aicontext <command> --help` prints the usage of one command.
- `export` and `status` refuse a project that `validate` reports errors for (for example an unsupported `specVersion`); warnings never block them. Export never writes or deletes outside the project (symlinks and junctions are resolved), and never touches a nested directory that has its own `.aicontext/`.

Current commands:

- `aicontext init [--path <directory>] [--name <project-name>] [--profile <core|extended>] [--force]`
- `aicontext --version`
- `aicontext validate [--path <directory>] [--strict]`
- `aicontext export [--target <agents|copilot|claude|cursor|windsurf|devin|aider>] [--path <directory>] [--layout <single|split>] [--force] [--dry-run] [--check]` (`--target` is optional when `exports.defaultTarget` is set; `--target` takes precedence)
- `aicontext export --target all [--path <directory>] [--layout <single|split>] [--force] [--dry-run] [--check]` (generates targets from `exports.targets`; if not set, generates all supported targets except `devin`)
- `aicontext status [--path <directory>] [--layout <single|split>]`: shows, per target, how much context is always on versus scoped/on-demand (with estimated tokens), whether the exports are in sync, and suggests the `split` layout when it would reduce always-on context.

### Rules and the split layout

By default every export is one file that contains all context. For larger projects, put guidance that only matters for part of the code into `.aicontext/rules/*.md` and set `"exports": { "layout": "split" }` (or pass `--layout split`):

```markdown
---
description: UI conventions for React components
paths: ["src/ui/**", "**/*.tsx"]
---

Use the shared design-system components.
```

- `paths` set: the rule applies only when working with matching files. Only `description` set: the agent loads it when relevant. Neither: always on.
- In the split layout `README.md` and `constraints.md` stay always on; scoped and on-demand content is exported as native rule files (Cursor `.mdc`, Copilot `.instructions.md`, Claude `.claude/rules`, Windsurf/Devin rules). Where a tool cannot scope content (AGENTS.md, Aider, and on-demand content in Copilot and Claude) it stays in the main file.
- Generated rule files are named `aicontext-<name>` and are removed when their source disappears; your own rule files are never touched.
- `devin` is opt-in (not part of the default `all` set) because Devin also loads `.windsurf/rules`.
- `exports.nestedAgents: true` (split layout only) writes rules scoped to an exact directory (`services/billing/**`) to `services/billing/AGENTS.md` instead of the root `AGENTS.md`, so tools that only read `AGENTS.md` (Codex, Jules, Junie, ...) load them only when working there. Rules with other patterns (`**/*.ts`, `src/ui/**/*.tsx`) or non-existent directories stay in the root file; `aicontext status` shows which and why. Note that Copilot, Cursor and Devin also read `AGENTS.md`, so combining this with their native rule targets can load a rule twice.
